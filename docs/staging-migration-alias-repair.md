# Staging migration filename reconciliation

This is a prepared, one-off repair for the failed hackathon staging run
[40090834811](https://github.com/Tembo-Tech-Ventures/ttv-website/actions/runs/40090834811).
Preparation and dry-run inspection do not authorize a live write. PM must approve
execution after Architect review and reserve the serialized staging slot. Do not
retry deployment while this decision is pending. No production target exists in
this script, and it is not wired into deployment or any workflow.

`8df53ce1-0e9d-4e51-aaac-329f84cf1d5f` named `ttv-website-db-staging`, and

`f62b2a39f8992a66f83875fc084de2850a1d7bbad6b80c57d153a60567a937a4`.
The live table, ten columns, defaults, primary key, `programId` foreign key, and

## Review and dry run

Use the exact reviewed supporting/integration commit. Invoke through SAM
`exec_with_secrets`, selecting managed `CF_API_TOKEN`; never pass a token as a
command argument, write it to a file, or use a literal placeholder. The command
runs from `web/`:

```sh
node scripts/cloudflare/staging-migration-alias.mjs --expected-version=4cabfd078a1b79722eae84ac868160f0f0f28393
```

Dry run is the default. The version is the expected **currently deployed**
Worker, not the failed candidate. The script rechecks account, Worker bindings,
D1 identity, exact custom/auth origin, version, migration digest, table/index and
ledger definitions, absence of ledger triggers and of a second ledger, and all
eight observed ledger IDs/names/timestamps and AUTOINCREMENT sequence (8 before, 9 after). It fails on any mismatch. It rejects
later migrations already present: do not loosen this one-off guard for a newer
state. Output contains metadata and the exact proposed bound SQL/parameters,
never student rows or secrets. Keep the dry-run receipt, hashes and reviewed SHA
in the private operational evidence record.

After Architect acceptance and explicit PM execution decision only, repeat the
same command with `--apply`. No agent should run it merely because this document
shows the command. It repeats the read-only inspection immediately before the
sole write. The statement is structurally:

```sql
INSERT INTO d1_migrations(name)
SELECT ? WHERE <exact observed ledger and sqlite_master predicates>
RETURNING id,name,applied_at;
```

The full predicates and parameters are generated by `aliasStatement` and shown
by the dry run. They atomically refuse an intervening ledger/schema/trigger
change. Exactly one returned row with ID 9 and the canonical name is required.
Readback checks the unchanged original rows and schema, the canonical row, and
before/after ledger hashes. Repeating before further migrations returns
`already-recorded` and performs no write. API errors and failed readback do not
cause automatic retry or rollback: a write may already have committed. Inspect
the live ledger before deciding what to do.

Record the managed execution job ID, approved script commit, expected Worker
version, timestamp, before/after metadata hashes, original legacy row and newly
returned canonical row. Reinspect the pending migration list. PM separately
decides when to retry the reviewed integration deployment; this script does not
deploy, run pending migrations, provision fixtures, or release the staging slot.

## Conditional inverse, not an automatic rollback

Normally retain this truthful alias permanently. If PM/Architect explicitly
authorize undo **before any later migration or deployment**, revalidate the same
staging boundary and ensure the ledger contains only the original eight rows
plus this exact recorded ninth row. Confirm that this execution created it
(`changed:true`), not an earlier run. A reviewed inverse may delete only the new
row using its exact ID/name/applied_at, with guards for the complete audited
ledger/schema. Do not copy a placeholder timestamp into an executable command:

```sql
DELETE FROM d1_migrations
WHERE id = 9 AND name = '0007_workable_nova.sql'
  AND applied_at = <exact recorded reconciliation timestamp>
  AND <unchanged audited ledger/schema predicates>;
```

The inverse must affect exactly one row and preserve all original metadata and
application data. It does not rewind `sqlite_sequence`; do not reset that value.
It also restores the original migration collision, so deployment stays paused.
If later migrations have run or the receipt/state differs, stop for a new plan.
There is deliberately no inverse CLI or automatic rollback.

## Validation

`staging-migration-alias.test.mjs` applies real migrations 0000–0006 plus the
historical SQL under its old name, reproduces the collision, inserts only the
canonical alias, retains original ledger rows and synthetic import data, tests
idempotence, and applies the remaining real 0008–0019 chain. Negative tests cover
wrong account/Worker bindings/D1/version/digest, ledger drift, missing/nonunique
index, altered table, second ledger, malicious ledger trigger, and races between
inspection and insertion. SQLite tests are local evidence, not a live D1 repair
or proof of authenticated product behavior.
